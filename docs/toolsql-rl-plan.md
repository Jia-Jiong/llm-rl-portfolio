# ToolSQL-RL 项目方案

调研日期为 2026 年 11 月 11 日。项目当前处于设计阶段，下文的参数、时间分配和验收标准都是计划值，实测结果将在实验记录中填写。

## 项目目标

训练一个能依据数据库结构生成 SQL、执行查询并利用环境反馈修正错误的小模型。研究执行奖励和有限轮次的交互训练能否提高跨数据库查询正确率，以及改善是否值得增加的生成开销。

输入为自然语言问题和数据库结构。模型可调用只读查询工具，最多试执行两次，随后提交最终 SQL。工具反馈包含执行错误或截断后的查询结果。评分器持有标准 SQL，模型只能看到任务与数据库。

示例任务为查询某个月成交金额最高的三个商品类别。模型需要选对表、连接键、时间过滤条件和聚合方式。SQL 可以成功执行，也可能因为连接或统计口径错误而得到错误结果，这些情况需要分别统计。

项目按大模型后训练、Agent 算法实习方向规划。已有的小模型构建、预训练和 SFT 工作可以作为简历里的另一段基础训练经历。主项目集中展示数据处理、奖励、训练、评测和错误归因。

## 数据与冷启动

1. 下载并核对 Spider 题目、schema、SQLite 文件与标准 SQL 的对应关系。用标准 SQL 做执行检查，将异常样本单独记录。
2. 在官方 train 内按 db_id 划分训练与调参验证集。同一数据库及其改写题保持在同一侧。
3. 第一轮选择约 1,000–3,000 条 SFT 样本，用已有标准 SQL 做监督。RL 首轮使用约 500–1,500 条训练问题，按训练侧采样的正确率检查难度。
4. 先统计每道题四个候选中全对、全错和有对有错的比例，再决定是否需要分层抽样。全错题需要更好的冷启动或更易的题，全对题的组内奖励缺乏差异。
5. 多轮 SFT 先从训练侧收集错误 SQL、真实工具反馈与修正后的 SQL。修正结果经执行验证后才进入训练，优先利用标准 SQL 构建终止动作。
6. 官方 Spider dev 留到方案固定后作最终公开基准评测。另制作少量新建 SQLite 库与人工核验问题，观察对新结构和统计口径的适应情况。

训练数据可以按完整 schema 的 token 长度过滤，保留过滤清单和覆盖率。评测使用统一的上下文预算，超过预算或超时的样本计入失败。公开数据可能已经进入基模的预训练，跨库划分只能控制本项目内的数据泄漏。

## 奖励与查询环境

单轮版本先使用二值最终奖励。最终 SQL 的结果与标准 SQL 在对应数据库上的结果一致则为 1，否则为 0。记录语法有效率、执行成功率与结果正确率三个指标。

奖励实现采用官方结果比较逻辑，保留重复行、排序和数值比较的处理约定。构造空结果、错误连接、错误聚合、重复行与排序等反例检查评分器。终端环境报错属于基础设施失败，单独记录和处理。

查询工具限制为只读 SQLite，设置连接权限和授权回调、超时、返回行数与结果长度上限。每条轨迹独立状态，屏蔽写库、附加数据库和扩展加载等能力。环境反馈与最终评分分开，标准 SQL 和标准结果只供评分使用。

多轮版本允许最多两次试执行，再提交 final_sql。模型可以依据真实错误或查询结果决定是否修正。评测时可获得的反馈与训练一致。轨迹训练只对模型生成的 token 计入策略损失，工具返回内容使用相应 mask。

主实验采用最终执行奖励。预算充足时再做小规模消融，将奖励改为“结果正确且额外工具调用更少时得分更高”，检查节省调用是否损害正确率。额外奖励只给正确完成的轨迹，权重在训练内部验证集选定。

## 对照实验

| 编号 | 模型处理方式 | 推理设置 | 回答的问题 |
| --- | --- | --- | --- |
| A | 原始 4B Instruct | 单次生成 | 起点能力如何 |
| B | SFT | 单次生成 | 监督适配贡献多少 |
| C | 从 B 出发做单轮 GRPO | 单次生成 | 执行奖励训练贡献多少 |
| D | 与多轮 RL 相同的冷启动 checkpoint | 两次试执行上限 | 仅增加执行反馈能改善多少 |
| E | 从 D 的 checkpoint 出发做多轮 GRPO | 与 D 相同的两次上限 | 交互轨迹训练的额外收益 |

如果需要额外的多轮冷启动 SFT，将其单独记录，D 和 E 共用该 checkpoint。先完成 A/B/C，形成首版实验。随后完成 D/E，让工具反馈与多轮训练各自的作用可被区分。

核心报告指标为首次生成结果正确率、最终结果正确率、执行有效率、工具调用次数、总生成 token、端到端时延、GPU 峰值显存和训练费用。最终采用官方测试套件评测，并保存逐题预测。SQL 字符串相同率可作为附加诊断指标。

除相同调用次数上限外，报告准确率随总生成 token 预算变化的结果。多轮调用的收益需要结合额外计算量解释。训练对照同时记录采样 token 和 GPU 小时，算法实验保持相同冷启动与预算口径。

先做一个主种子跑通全链路，再优先给最终 B/C 或 D/E 的关键对照补两个种子。评测不确定性可按数据库分组 bootstrap，预算不足时清楚标注单种子结果。每次挑选 checkpoint 使用训练内部验证集。

优先选一个改进点做消融，例如普通抽样与基于训练侧难度的分层抽样，或最终执行奖励与正确轨迹的调用成本奖励。分层采样实验需计入筛选所消耗的 rollout，并保留少量困难样本以避免长期排除全错任务。

## AutoDL 资源方案

AutoDL 官方说明，同一个实例内的多卡位于同一物理主机，支持单机多卡。创建时选择 GPU 数量，按量计费实例也可关机后升降配置，CPU 与内存随卡数相应调整。选择主机时还需检查同机空闲卡数。[单机多卡说明](https://www.autodl.com/docs/distributed_training/) · [常见问题](https://www.autodl.com/docs/qa/) · [升降配置](https://www.autodl.com/docs/update_config/)

首选候选是同一实例内的双 4090。GPU 0 放 4B 的 LoRA trainer，GPU 1 放 vLLM sampler，采样使用 tensor parallel size 1。训练与采样通过本机通信和框架的权重同步机制连接，先用十几步检查更新后的采样确实来自当前策略。这个配置的角色是训练与采样分卡，简历中按实际架构描述。

两张 24GB 卡各自具有独立的显存。DDP 在每卡复制模型，FSDP/ZeRO 才会显式分片。对于当前 4B LoRA 项目，训练与采样分卡是可先验证的配置。检查驱动、CUDA、NCCL、拓扑、通信带宽与框架兼容性后再确定正式资源。

如果双 4090 出现内存或通信瓶颈，可在同一预算内换单张 A800 80GB，用 TRL colocate 和合适的显存分配运行。比较端到端每训练步的费用，再选择整轮实验配置。AutoDL 首页检索到的公开标价包括 4090 24GB 约 1.88 元/时、A800 80GB 约 5.59 元/时，订单价格与库存以租用当时为准。[平台标价](https://www.autodl.com/)

AutoDL 的普通实例采用容器，官方说明容器内无法直接使用 Docker。本项目的 SQLite 执行器可以在容器内运行。[实例说明](https://www.autodl.com/docs/env/)

| 设置 | 起始计划 |

## 四周实施节奏

1. 第一周搭建 SQLite 环境和结果评测，跑起点模型，导出约 100 条内部验证样本的错误分类，再完成小规模 SFT。
2. 第二周实现执行奖励、跑单轮 GRPO，完成 A/B/C，记录显存、生成速度和训练曲线。
3. 第三周接入两次执行机会的交互，构建并验证多轮冷启动数据，完成 D/E 的小规模训练和比较。
4. 第四周按剩余预算完成一个消融和关键复跑，固定方案后运行最终评测，整理模型卡、复现说明和演示。

每一步先讲清概念与数据流，再逐个模块实现。第一个可运行成果应是本地 SQLite 奖励与评测示例，用手写 SQL 检查“能执行”和“结果正确”的差别，之后接模型推理。
